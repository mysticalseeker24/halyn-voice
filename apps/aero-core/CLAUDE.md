# apps/aero-core — the mock bank (separate Worker + D1)

This is "the bank's system", deliberately separate from Halyn. It must behave like a real core system that only
accepts writes carrying a valid Halyn grant. Contract: `docs/API.md` → "Aero Core"; routes and response schemas:
`packages/shared/src/core.ts` (`CORE_ROUTES`, `CORE_RESPONSES`); tables: `docs/DATA_MODEL.md` → "D1".

## Layout
```
src/index.ts          Worker entry: createApp() with the system clock and WebCrypto rng
src/app.ts            Hono app: /health, one route per CORE_ROUTES endpoint (env → grant → execute)
src/env.ts            Zod env: DB, AERO_TENANT_ID (wrangler.toml var), HALYN_PUBLIC_JWKS (secret); fails closed
src/grant/            requireGrant (@halyn/sdk verifyGrant + strict params), readParams (query / JSON body)  ≥95%
src/core/             commit.ts (jti + effect in ONE D1 batch, REUSED vs FAIL_CLOSED)  ≥95%; one handler per action
                      group: cards, fees, loans, transfers (3 actions), accounts (balance, statement); execute.ts
src/db/               Drizzle sqlite-core schema (every table has tenant_id) + client
src/seed/             deterministic demo rows (seed-data.ts) → SQL (seed-sql.ts); same template for tests
src/http/             error envelope (reason code → status), masked JSON request log
migrations/           drizzle-kit SQL (committed): `pnpm --filter @halyn/aero-core db:generate` after a schema change
seed/seed.sql         generated by `pnpm seed:core` (a unit test keeps it equal to src/seed)
test/                 setup.ts (migrations), fixtures (grants signed with a per-run throwaway key, seeded customers),
                      int/ (every 401 path, concurrent double-spend, scenario steps on the demo seed)
```

## Rules here
- Every route — reads too — requires `x-halyn-grant`, checked by `requireGrant` → `@halyn/sdk.verifyGrant` with the
  route's action list, the exact params (query string or JSON body), and `expectedTenant = AERO_TENANT_ID`. Then the
  params must pass the action's strict schema. The route acts only on the rows of `claims.sub`.
- Single use: the effect is ONE `db.batch([...])` that starts with `recordGrant` (insert the jti into `used_grants`).
  A replay fails the primary key and rolls the whole batch back. Write handlers look the jti up first (with their
  reads, one round trip) so a replay is `E_GRANT_REUSED` before any business check. A refused write (400/404) does not
  use the grant; a read uses it even when the account is missing.
- Errors: 401 `E_GRANT_MISSING | E_GRANT_INVALID | E_GRANT_EXPIRED | E_GRANT_REUSED | E_PARAMS_MISMATCH`; 400
  `E_BAD_REQUEST` (already waived, wrong amount, balance too low, closed loan, blocked account); 404 `E_NOT_FOUND`;
  500 `E_FAIL_CLOSED` (config missing, a batch the database refused). Any error: nothing was written.
- No business rules here beyond balances and basic validation — policy lives in Halyn. Balances never go negative
  (checked up front, and a `CHECK (balance_minor >= 0)` rolls back a racing overdraft); a fee is credited once (a
  unique index on fee_waiver transactions).
- Money is INTEGER minor units + currency. Every query filters on `tenant_id` (and `customer_ref`).
- Seed: `pnpm seed:core` (local D1: applies migrations, then `seed/seed.sql`; resets the demo customers, never
  `used_grants`). `--write-only` regenerates the file; `--remote --yes` targets the deployed D1 (go-ahead first).
- Tests generate their own Ed25519 keys (vitest.config.ts); bindings are explicit, so `.dev.vars` never leaks in.
  Each test seeds a fresh customer (`seedCustomer()`); only `test/int/scenarios.test.ts` uses the demo ids.
